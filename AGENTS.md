## 2. Mandatory Build & Deployment Rules

### Rule 1: Every Build Must Be Versioned
- Every build generated by an agent or developer must have:
  - **`versionCode` / `buildNumber`**: An integer that strictly auto-increments with each build (or is derived from build counter / timestamp).
  - **`versionName`**: Semantic versioning format (`MAJOR.MINOR.PATCH`, e.g., `1.0.0`, `1.0.1`, `1.1.0`).
- Never deploy an artifact with an unincremented or duplicate version/build number.
- Keep a persistent version tracker file (e.g., `version.properties` or `package.json`):
  ```properties
  VERSION_MAJOR=1
  VERSION_MINOR=0
  VERSION_PATCH=0
  BUILD_NUMBER=1
  ```

### Rule 2: Automatic Delivery to Cloud / Local Sync Directory
- Whenever a build (`npm run build`) finishes successfully, the output artifact must automatically be copied/moved to the sync directory: `C:\Users\matth\Desktop\vibe-projects\open-img\builds\open-img-Builds\`.
- The build process or agent must verify that the file exists at the destination after the transfer.

### Rule 3: Artifact Naming Convention
All build artifacts exported to the sync directory must follow this standardized naming pattern:
```
open-img-v{versionName}-build{versionCode}-{buildType}-{timestamp}.zip
```
**Example:**
`open-img-v1.0.2-build14-release-20260914-0445.zip`

### Rule 4: Build Metadata & Changelog Logging
- Alongside every artifact copied to the sync directory, generate or update a `build-history.json` or `build-history.md` recording:
  - File name & size (MB)
  - Date & Timestamp
  - Version number & code
  - Build type (`debug` / `release`)
  - Commit hash or brief change summary

### Rule 5: Always Upload / Push to GitHub
- **MANDATORY:** Every commit, feature merge, and build update MUST immediately be pushed to the remote GitHub repository (`origin`).
- No task or feature is considered complete until all local commits on `develop` (and active feature branches) are synced to `origin`.
- Commands required upon finishing any work:
  ```bash
  git push origin develop
  ```
  *(For feature branches prior to or during merge: `git push -u origin feature/<feature-name>`)*
- **NEVER push or merge directly to `main`** — only the user merges to and pushes `main`.

## 5. Git Branching & Workflow Rules (Three-Stage Strategy)

All changes, enhancements, and features must follow a strict three-stage Git workflow with automatic remote synchronization:

```
┌─────────────────────────────────────────────────────────────┐
│                 GitHub Remote (origin)                      │
│   origin/main (User Only)      origin/develop (Agents Sync) │
└──────────────▲──────────────────────────────▲───────────────┘
               │                              │
               │ USER ONLY: Release & Push    │ git push origin develop
┌──────────────┴───────────────┐   USER ONLY  ┌───────────┐
│           main               │◄─────────────┤  develop  │  (Stage 2: Integration Baseline)
└──────────────────────────────┘   Merge/Tag  └───▲───────┘
                                                  │
                                                  │ Merge & push
                                                  ▼
                                       ┌──────────────────┐
                                       │ feature/<name>   │  (Stage 3: Feature Branches — Agents)
                                       └──────────────────┘
```

> [!CAUTION]
> ### 🛑 STRICT AGENT RULE: NEVER MERGE TO `main`
> **ONLY THE USER (HUMAN MAINTAINER) IS ALLOWED TO MERGE INTO `main` OR TAG RELEASES.**
> Under NO circumstances should an AI agent, automated tool, or script execute `git checkout main` or merge into `main`.
> An agent's work is complete when changes are merged into `develop`, verified, and **pushed to GitHub (`git push origin develop`)**.

### Stage 1: `main` (Production / Stable Releases — USER ONLY)
- **Role:** Production-ready code.
- **STRICTLY RESERVED FOR THE USER:** Agents must NEVER commit, checkout, or merge directly into `main`.
- Only receives merges from `develop` when the **USER** personally decides to release, test, and tag a milestone.
- Every commit on `main` corresponds to a verified release with an exported artifact in the sync target directory and a release tag pushed to GitHub.

### Stage 2: `develop` (Integration / Staging Baseline)
- **Role:** The primary integration branch where completed features are accumulated and tested together.
- This is the baseline from which all feature branches are cut.
- When a feature is completed, tested, and approved, it is merged back into `develop`.
- Agents perform builds and automated unit test runs against `develop`.
- **MANDATORY:** Always push `develop` to GitHub immediately after merging: `git push origin develop`.

### Stage 3: `feature/*` (Feature Branches — Mandatory for Every Request)
- **Rule:** For **ANY** new feature request, enhancement, or sub-feature requested by the user:
  1. The agent MUST create a new feature branch cut from `develop`:
     ```bash
     git checkout develop
     git pull origin develop
     git checkout -b feature/<feature-name>
     ```
  2. Implement, test, and make sensible atomic commits on the `feature/<feature-name>` branch.
  3. Optionally push feature branch to GitHub for backup/collaboration:
     ```bash
     git push -u origin feature/<feature-name>
     ```
  4. Once verified and all unit tests pass, merge the feature branch into `develop`:
     ```bash
     git checkout develop
     git merge --no-ff feature/<feature-name>
     ```
  5. **MANDATORY — ALWAYS PUSH TO GITHUB:**
     ```bash
     git push origin develop
     ```
  6. **STOP — DO NOT MERGE TO `main`:**
     Report the completion, unit test results, and verified changes to the user on the `develop` branch.
     The user will review `develop` and personally handle merging into `main`, tagging, and pushing:
     ```bash
     # (USER ACTION ONLY)
     git checkout main
     git merge --no-ff develop
     git tag -a v<versionName> -m "Release v<versionName>"
     git push origin main --tags
     ```
